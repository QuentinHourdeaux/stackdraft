# Stackdraft v0.1 Product Specification

> **Stackdraft — track what you're building.**

Status: Draft for implementation\
Target: Personal proof of concept\
Primary user: A software engineer tracking personal Stacks\
Deployment: One self-hosted instance on a trusted local network

Canonical product terms are defined in
[`domain-language.md`](domain-language.md).

## 1. Purpose

Stackdraft is a lightweight, self-hosted tracker for software engineers working
on personal Stacks. It provides one dependable place to capture Stacks and the
Drafts inside them without introducing the process, collaboration features, or
administration of a team-oriented project-management product.

Version 0.1 is successful if it becomes the user's natural place to record and
review ongoing development work.

## 2. Product principles

1. **Capture must be fast.** Recording a Draft should take seconds.
2. **Developer work is the domain.** Stackdraft is not a general company or life
   planner.
3. **The workflow belongs to the user.** Stack and Draft States are configured
   in the UI, not defined as application constants.
4. **Local ownership matters.** The application and its data must be easy to
   run, back up, and move between machines.
5. **Small before clever.** v0.1 validates daily usefulness; it does not
   anticipate every future feature.

## 3. v0.1 scope

### 3.1 Stacks

The user can:

- View all Stacks.
- Create a Stack with a title, description, and State.
- Open a Stack.
- Edit its title, description, and State.
- Filter Stacks by State.

A Stack contains:

- `id`
- `title`
- `description`
- `stateId`
- `createdAt`
- `updatedAt`

### 3.2 Drafts

A **Draft** is a scoped unit of engineering work within a Stack. It may
represent a feature, bug fix, refactor, experiment, or investigation without
requiring a separate type system.

The user can:

- View the Drafts in a Stack.
- Quickly add a Draft from the Stack page.
- Create a Draft with a title, description, and State.
- Open a Draft.
- Edit its title, description, and State.
- Filter a Stack's Drafts by State.

A Draft contains:

- `id`
- `stackId`
- `title`
- `description`
- `stateId`
- `createdAt`
- `updatedAt`

### 3.3 State configuration

Stack States and Draft States are separate workflows.

The user can:

- View Stack States and Draft States.
- Create a State with a name and color.
- Edit a State's name and color.
- Reorder States.
- Choose the default State for newly created Stacks or Drafts.
- Delete a State only when it is unused, is not the default, and is not the only
  State in its scope.

A State contains:

- `id`
- `scope`: `stack` or `draft`
- `name`
- `color`
- `position`
- `isDefault`
- `createdAt`
- `updatedAt`

The database is initialized with editable starter States:

- Stacks: Planned, Active, Paused, Completed
- Drafts: Backlog, Todo, In Progress, Done, Canceled

These are ordinary database rows seeded by the initial migration. The
application does not branch on their names or IDs.

### 3.4 Screens

#### Stacks `/`

- Stackdraft application shell
- Stack-State filter
- Stack list
- Create-Stack action
- Useful empty state when no Stacks exist

#### Stack detail `/stacks/:stackId`

- Stack title, description, and State
- Edit-Stack action
- Quick-add Draft input
- Draft-State filter
- Draft list
- Useful empty state when the Stack has no Drafts

#### Draft detail `/stacks/:stackId/drafts/:draftId`

- Draft title, description, and State
- Edit controls
- Link back to its Stack

#### State settings `/settings/states`

- Separate Stack-State and Draft-State sections
- Create, edit, reorder, set-default, and delete-when-unused controls

## 4. Core user flows

### First-run flow

1. The user opens Stackdraft.
2. The Stack list is empty and offers a clear create action.
3. The user creates a Stack using the default Stack State.
4. Stackdraft opens the new Stack's detail page.
5. The user quickly adds the first Draft using the default Draft State.

### Daily capture flow

1. The user opens a Stack.
2. The quick-add field is immediately available.
3. The user enters a title and submits.
4. The Draft appears without leaving the Stack page.
5. Description and State can be refined immediately or later.

### Workflow customization flow

1. The user opens State settings.
2. The user creates or edits a State.
3. The change is immediately available in Stack or Draft forms.
4. Existing records retain their assigned State.

## 5. UX requirements

- Creating a Draft from a Stack requires only a title; description and State may
  use defaults.
- All forms show validation errors next to the relevant field.
- Destructive State deletion requires confirmation.
- Loading, empty, and recoverable error states are visible and understandable.
- The interface works at typical desktop and laptop widths.
- Keyboard navigation and visible focus states are supported.
- State is never communicated by color alone; its name is always visible.
- Descriptions are plain text in v0.1. Markdown rendering is deferred.
- The initial view is list-based. Kanban and drag-and-drop are deferred.

## 6. Data and API contract

All IDs are UUID strings generated by the application. API timestamps are UTC
ISO-8601 strings; backend definitions and schemas use DateTime-specific
primitives rather than plain strings.

### Stack endpoints

- `GET /api/stacks?stateId=...`
- `POST /api/stacks`
- `GET /api/stacks/:stackId`
- `PATCH /api/stacks/:stackId`

### Draft endpoints

- `GET /api/stacks/:stackId/drafts?stateId=...`
- `POST /api/stacks/:stackId/drafts`
- `GET /api/stacks/:stackId/drafts/:draftId`
- `PATCH /api/stacks/:stackId/drafts/:draftId`

### State endpoints

- `GET /api/states?scope=stack|draft`
- `POST /api/states`
- `PATCH /api/states/:stateId`
- `PUT /api/states/:stateId/position`
- `PUT /api/states/:stateId/default`
- `DELETE /api/states/:stateId`

### Operational endpoint

- `GET /api/health`

### Error shape

API errors use one predictable JSON shape:

```json
{
  "error": {
    "code": "STATE_IN_USE",
    "message": "This State is assigned to existing Drafts.",
    "details": {}
  }
}
```

Expected error classes:

- Validation error: `400`
- Resource not found: `404`
- Conflict, such as deleting an in-use State: `409`
- Unexpected server error: `500`

## 7. Data model

```text
states
├── id TEXT PRIMARY KEY
├── scope TEXT NOT NULL CHECK (scope IN ('stack', 'draft'))
├── name TEXT NOT NULL
├── color TEXT NOT NULL
├── position INTEGER NOT NULL
├── is_default INTEGER NOT NULL
├── created_at TEXT NOT NULL
└── updated_at TEXT NOT NULL

stacks
├── id TEXT PRIMARY KEY
├── title TEXT NOT NULL
├── description TEXT NOT NULL DEFAULT ''
├── state_id TEXT NOT NULL → states.id
├── created_at TEXT NOT NULL
└── updated_at TEXT NOT NULL

drafts
├── id TEXT PRIMARY KEY
├── stack_id TEXT NOT NULL → stacks.id
├── title TEXT NOT NULL
├── description TEXT NOT NULL DEFAULT ''
├── state_id TEXT NOT NULL → states.id
├── created_at TEXT NOT NULL
└── updated_at TEXT NOT NULL

schema_migrations
├── version TEXT PRIMARY KEY
└── applied_at TEXT NOT NULL
```

Required database rules:

- Foreign-key enforcement is enabled.
- State names are unique within a scope, case-insensitively.
- Exactly one default State exists per scope.
- A Stack's State must have `stack` scope.
- A Draft's State must have `draft` scope.
- Drafts are indexed by `stack_id` and `state_id`.
- Stacks are indexed by `state_id`.

Scope consistency and the single-default invariant may require transactions or
database triggers because ordinary SQLite foreign keys cannot express them
fully.

## 8. Technical architecture

### Runtime and backend

- Deno 2.x, pinned to a specific version
- TypeScript
- Oak for HTTP routing and static-file serving
- Effect for core services, typed errors, configuration, logging, and store
  dependencies
- Effect Schema for request and response validation
- Deno's built-in `node:sqlite` module
- Explicit SQL migrations

### Frontend

- React 19
- TypeScript
- Vite
- React Router
- Plain CSS with a small token layer using CSS custom properties
- Native `fetch` behind a small typed API-client module

### Deployment

- One production application container
- The Deno process serves both `/api/*` and the compiled React assets
- SQLite is stored at `/data/stackdraft.sqlite`
- Docker Compose bind-mounts a local `./data` directory to `/data`
- No cache service
- No reverse proxy is required for v0.1

### Development topology

- Vite development server provides frontend hot reload.
- The Deno API runs separately.
- Vite proxies `/api` requests to Deno.
- Production remains a single-origin application.

## 9. Security boundary

v0.1 has no accounts, authentication, or authorization. It is intended for one
user on a trusted local network.

Consequences:

- Anyone who can reach the exposed port can read and modify all data.
- The README must state this prominently.
- The container must not be exposed directly to the public internet.
- Authentication is a post-v0.1 feature and becomes mandatory before any
  public-hosting story.

## 10. Portability and backup

The repository contains:

- Application source
- Pinned dependencies
- Docker configuration
- Database migrations
- Operating documentation

User data lives only in the mounted `./data` directory.

Moving to another machine:

1. Stop Stackdraft.
2. Copy the repository and `data` directory.
3. Install Docker.
4. Run `docker compose up -d --build`.

The documented v0.1 backup procedure stops the application before copying the
database file. An online SQLite backup command may be added later.

## 11. Explicit non-goals

v0.1 does not include:

- Multiple users, accounts, or permissions
- Public internet deployment
- Teams, assignees, comments, or notifications
- Nested Drafts or Draft relationships
- Labels, priorities, estimates, due dates, or cycles
- Attachments
- GitHub or GitLab integration
- AI features
- Idea board
- Global inbox
- Search
- Kanban, drag-and-drop, or custom views
- Markdown or rich-text editing
- Real-time updates or web sockets
- Offline clients or synchronization logic
- Import/export beyond filesystem-level backup
- Stack or Draft deletion
- Caching infrastructure

## 12. Acceptance criteria

v0.1 is complete when:

1. A fresh Docker Compose deployment starts successfully with one command.
2. The database is created and migrated automatically.
3. The UI can create and edit Stacks.
4. The UI can create and edit Drafts within a Stack.
5. Stack and Draft States can be managed from the UI.
6. New Stacks and Drafts receive their configured default States.
7. Stacks and Drafts can be filtered by State.
8. Data survives container replacement and host restart.
9. The documented stop-and-copy backup can be restored on another machine.
10. Core service and store behavior has automated tests.
11. The frontend handles loading, empty, validation, and API-error states.
12. After several days of real use, the user chooses Stackdraft over temporary
    notes for capturing development work.

## 13. Deferred decisions

These should be informed by using v0.1 rather than designed upfront:

- Whether an inbox is more useful than immediate Stack assignment
- Whether Drafts need types such as feature, bug, or experiment
- Whether descriptions should support Markdown
- Whether Stack and Draft deletion are necessary
- Whether a Kanban view improves the workflow
- How the future idea board relates to Stacks and Drafts
- How AI tools authenticate and interact with Stackdraft
- Whether Git repositories become first-class entities
