# Stackdraft v0.1 Product Specification

> **Stackdraft — track what you're building.**

Status: Draft for implementation\
Target: Personal proof of concept\
Primary user: A software engineer tracking personal development projects\
Deployment: One self-hosted instance on a trusted local network

## 1. Purpose

Stackdraft is a lightweight, self-hosted tracker for software engineers working
on personal projects. It provides one dependable place to capture projects and
the work items inside them without introducing the process, collaboration
features, or administration of a team-oriented project-management product.

Version 0.1 is successful if it becomes the user's natural place to record and
review ongoing development work.

## 2. Product principles

1. **Capture must be fast.** Recording a work item should take seconds.
2. **Developer work is the domain.** Stackdraft is not a general company or life
   planner.
3. **The workflow belongs to the user.** Project and item statuses are
   configured in the UI, not defined as application constants.
4. **Local ownership matters.** The application and its data must be easy to
   run, back up, and move between machines.
5. **Small before clever.** v0.1 validates daily usefulness; it does not
   anticipate every future feature.

## 3. v0.1 scope

### 3.1 Projects

The user can:

- View all projects.
- Create a project with a title, description, and status.
- Open a project.
- Edit its title, description, and status.
- Filter projects by status.

A project contains:

- `id`
- `title`
- `description`
- `statusId`
- `createdAt`
- `updatedAt`

### 3.2 Work items

The UI calls project-level tickets **items**. An item may represent a feature,
bug, technical task, experiment, or investigation without requiring a separate
item-type system.

The user can:

- View the items in a project.
- Quickly add an item from the project page.
- Create an item with a title, description, and status.
- Open an item.
- Edit its title, description, and status.
- Filter a project's items by status.

An item contains:

- `id`
- `projectId`
- `title`
- `description`
- `statusId`
- `createdAt`
- `updatedAt`

### 3.3 Status configuration

Project statuses and item statuses are separate workflows.

The user can:

- View project statuses and item statuses.
- Create a status with a name and color.
- Edit a status's name and color.
- Reorder statuses.
- Choose the default status for newly created projects or items.
- Delete a status only when it is unused, is not the default, and is not the
  only status in its scope.

A status contains:

- `id`
- `scope`: `project` or `item`
- `name`
- `color`
- `position`
- `isDefault`
- `createdAt`
- `updatedAt`

The database is initialized with editable starter statuses:

- Projects: Planned, Active, Paused, Completed
- Items: Backlog, Todo, In Progress, Done, Canceled

These are ordinary database rows seeded by the initial migration. The
application does not branch on their names or IDs.

### 3.4 Screens

#### Projects `/`

- Stackdraft application shell
- Project-status filter
- Project list
- Create-project action
- Useful empty state when no projects exist

#### Project detail `/projects/:projectId`

- Project title, description, and status
- Edit-project action
- Quick-add item input
- Item-status filter
- Item list
- Useful empty state when the project has no items

#### Item detail `/projects/:projectId/items/:itemId`

- Item title, description, and status
- Edit controls
- Link back to its project

#### Status settings `/settings/statuses`

- Separate project-status and item-status sections
- Create, edit, reorder, set-default, and delete-when-unused controls

## 4. Core user flows

### First-run flow

1. The user opens Stackdraft.
2. The project list is empty and offers a clear create action.
3. The user creates a project using the default project status.
4. Stackdraft opens the new project's detail page.
5. The user quickly adds the first item using the default item status.

### Daily capture flow

1. The user opens a project.
2. The quick-add field is immediately available.
3. The user enters a title and submits.
4. The item appears without leaving the project page.
5. Description and status can be refined immediately or later.

### Workflow customization flow

1. The user opens status settings.
2. The user creates or edits a status.
3. The change is immediately available in project or item forms.
4. Existing records retain their assigned status.

## 5. UX requirements

- Creating an item from a project requires only a title; description and status
  may use defaults.
- All forms show validation errors next to the relevant field.
- Destructive status deletion requires confirmation.
- Loading, empty, and recoverable error states are visible and understandable.
- The interface works at typical desktop and laptop widths.
- Keyboard navigation and visible focus states are supported.
- Status is never communicated by color alone; its name is always visible.
- Descriptions are plain text in v0.1. Markdown rendering is deferred.
- The initial view is list-based. Kanban and drag-and-drop are deferred.

## 6. Data and API contract

All IDs are UUID strings generated by the application. All timestamps are UTC
ISO-8601 strings.

### Project endpoints

- `GET /api/projects?statusId=...`
- `POST /api/projects`
- `GET /api/projects/:projectId`
- `PATCH /api/projects/:projectId`

### Item endpoints

- `GET /api/projects/:projectId/items?statusId=...`
- `POST /api/projects/:projectId/items`
- `GET /api/projects/:projectId/items/:itemId`
- `PATCH /api/projects/:projectId/items/:itemId`

### Status endpoints

- `GET /api/statuses?scope=project|item`
- `POST /api/statuses`
- `PATCH /api/statuses/:statusId`
- `PUT /api/statuses/:statusId/position`
- `PUT /api/statuses/:statusId/default`
- `DELETE /api/statuses/:statusId`

### Operational endpoint

- `GET /api/health`

### Error shape

API errors use one predictable JSON shape:

```json
{
  "error": {
    "code": "STATUS_IN_USE",
    "message": "This status is assigned to existing items.",
    "details": {}
  }
}
```

Expected error classes:

- Validation error: `400`
- Resource not found: `404`
- State conflict, such as deleting an in-use status: `409`
- Unexpected server error: `500`

## 7. Data model

```text
statuses
├── id TEXT PRIMARY KEY
├── scope TEXT NOT NULL CHECK (scope IN ('project', 'item'))
├── name TEXT NOT NULL
├── color TEXT NOT NULL
├── position INTEGER NOT NULL
├── is_default INTEGER NOT NULL
├── created_at TEXT NOT NULL
└── updated_at TEXT NOT NULL

projects
├── id TEXT PRIMARY KEY
├── title TEXT NOT NULL
├── description TEXT NOT NULL DEFAULT ''
├── status_id TEXT NOT NULL → statuses.id
├── created_at TEXT NOT NULL
└── updated_at TEXT NOT NULL

items
├── id TEXT PRIMARY KEY
├── project_id TEXT NOT NULL → projects.id
├── title TEXT NOT NULL
├── description TEXT NOT NULL DEFAULT ''
├── status_id TEXT NOT NULL → statuses.id
├── created_at TEXT NOT NULL
└── updated_at TEXT NOT NULL

schema_migrations
├── version TEXT PRIMARY KEY
└── applied_at TEXT NOT NULL
```

Required database rules:

- Foreign-key enforcement is enabled.
- Status names are unique within a scope, case-insensitively.
- Exactly one default status exists per scope.
- A project's status must have `project` scope.
- An item's status must have `item` scope.
- Items are indexed by `project_id` and `status_id`.
- Projects are indexed by `status_id`.

Scope consistency and the single-default invariant may require transactions or
database triggers because ordinary SQLite foreign keys cannot express them
fully.

## 8. Technical architecture

### Runtime and backend

- Deno 2.x, pinned to a specific version
- TypeScript
- Oak for HTTP routing and static-file serving
- Effect for domain services, typed errors, configuration, logging, and
  repository dependencies
- Effect Schema for request and response validation
- Deno's built-in `node:sqlite` module
- Explicit SQL migrations

### Frontend

- React 19
- TypeScript
- Vite
- React Router
- Plain CSS with a small token layer using CSS custom properties
- Native `fetch` behind a small typed API-client module

### Deployment

- One production application container
- The Deno process serves both `/api/*` and the compiled React assets
- SQLite is stored at `/data/stackdraft.sqlite`
- Docker Compose bind-mounts a local `./data` directory to `/data`
- No cache service
- No reverse proxy is required for v0.1

### Development topology

- Vite development server provides frontend hot reload.
- The Deno API runs separately.
- Vite proxies `/api` requests to Deno.
- Production remains a single-origin application.

## 9. Security boundary

v0.1 has no accounts, authentication, or authorization. It is intended for one
user on a trusted local network.

Consequences:

- Anyone who can reach the exposed port can read and modify all data.
- The README must state this prominently.
- The container must not be exposed directly to the public internet.
- Authentication is a post-v0.1 feature and becomes mandatory before any
  public-hosting story.

## 10. Portability and backup

The repository contains:

- Application source
- Pinned dependencies
- Docker configuration
- Database migrations
- Operating documentation

User data lives only in the mounted `./data` directory.

Moving to another machine:

1. Stop Stackdraft.
2. Copy the repository and `data` directory.
3. Install Docker.
4. Run `docker compose up -d --build`.

The documented v0.1 backup procedure stops the application before copying the
database file. An online SQLite backup command may be added later.

## 11. Explicit non-goals

v0.1 does not include:

- Multiple users, accounts, or permissions
- Public internet deployment
- Teams, assignees, comments, or notifications
- Sub-items or item relationships
- Labels, priorities, estimates, due dates, or cycles
- Attachments
- GitHub or GitLab integration
- AI features
- Idea board
- Global inbox
- Search
- Kanban, drag-and-drop, or custom views
- Markdown or rich-text editing
- Real-time updates or web sockets
- Offline clients or synchronization logic
- Import/export beyond filesystem-level backup
- Project or item deletion
- Caching infrastructure

## 12. Acceptance criteria

v0.1 is complete when:

1. A fresh Docker Compose deployment starts successfully with one command.
2. The database is created and migrated automatically.
3. The UI can create and edit projects.
4. The UI can create and edit items within a project.
5. Project and item statuses can be managed from the UI.
6. New projects and items receive their configured default statuses.
7. Projects and items can be filtered by status.
8. Data survives container replacement and host restart.
9. The documented stop-and-copy backup can be restored on another machine.
10. Core service and repository behavior has automated tests.
11. The frontend handles loading, empty, validation, and API-error states.
12. After several days of real use, the user chooses Stackdraft over temporary
    notes for capturing development work.

## 13. Deferred decisions

These should be informed by using v0.1 rather than designed upfront:

- Whether an inbox is more useful than immediate project assignment
- Whether items need types such as feature, bug, or experiment
- Whether descriptions should support Markdown
- Whether project and item deletion are necessary
- Whether a Kanban view improves the workflow
- How the future idea board relates to projects and items
- How AI tools authenticate and interact with Stackdraft
- Whether Git repositories become first-class entities
